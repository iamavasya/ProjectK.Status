# Статус Лілейки

Cloudflare Worker на безкоштовному плані з двома задачами. Він веде публічну сторінку стану сервісів Лілейки на `status.lileyka.app` і збирає анонімну телеметрію від її інстансів: селф-хост бандлів і проду.

## Що він робить

- **Перевірки.** Кожні 2 хвилини перевіряються всі цілі з `TARGETS`: API, вебзастосунок, каталог вмілостей і документація. Перевіряє не сам крон, а Durable Object `Prober`, закріплений біля Східної Європи (див. нижче).
- **Сторінка статусу** (`/`). Показує стан кожної цілі зараз, смужки за 90 днів, середній час відповіді за 24 години, оголошення та історію змін стану за 14 днів.
- **Адмінка** (`/admin`, за Cloudflare Access). Показує живі інстанси, їхні версії, краї, країни й навантаження. Там же пишуться оголошення: збій, роботи, примітка.
- **Телеметрія.** Інстанс шле пінг і у відповідь дізнається номер найновішого релізу.
- **Сповіщення в Telegram.** Приходять, коли ціль упала або піднялася, і коли інстанс мовчить понад 3 дні. Без токена бота сповіщення вимкнені.

## Як рахується стан

Одна перевірка дає один із трьох станів:

| Стан | Коли |
| --- | --- |
| `up` | 2xx швидше за `SLOW_MS` (3 с), а для цілей типу `health` ще й `status: "ready"` |
| `degraded` | відповідь повільніша за `SLOW_MS` або `/health` не `ready` |
| `down` | помилка мережі, не-2xx або немає відповіді за `TIMEOUT_MS` (10 с) |

Якщо перевірка не дала `up`, вона повторюється через 2 с, і зараховується краща з двох відповідей. Так поодиноке обірване з'єднання не фарбує день.

**Звідки міряємо.** Крон Cloudflare щоразу запускається в новій локації, за добу їх набирається понад 30, серед них Мельбурн і Токіо. Звідти до API в Польщі 1–1,3 с, а часом з'єднання не встигає і за 10 с. Усі «падіння» на сторінці 16–17.10.2026 були саме такі: Cloudflare фіксував 499, Azure так і не відповів, і щоразу з MEL, BNE чи NRT. Справжні користувачі, які заходять через Відень і Варшаву, жодного збою не мали. Тому крон лише викликає Durable Object `Prober` з підказкою розташування `eeur`. Об'єкт створюється один раз поряд зі Східною Європою, там лишається і робить проби. Якщо об'єкт недоступний, крон перевіряє сам і пише про це в лог.

Колір дня чи години на сторінці:

- **червоний** — якщо `down` становить від 1 % перевірок, тобто приблизно 15 хв на добу;
- **жовтий** — якщо була хоч одна `down` або щонайменше 5 % перевірок мали стан `degraded`;
- **зелений** — в інших випадках.

Доступність рахується як частка перевірок без `down`.

Для API графік показує **час обробки в самому API**, а не час відповіді. Цей час Лілейка віддає в `/health` полем `api`: медіана її власного часу на справжніх запитах за останні 15 хв. Самі перевірки й CORS-preflight туди не входять. Час відповіді — це здебільшого мережа між Cloudflare і Azure, а не робота API, тому для API він лишається лише в даних. Година без жодного запиту до API сіра. Цілі без поля `api` (веб, каталог, документація) показують середній час відповіді по перевірках, де щось відповіло.

## Дані

Усе зберігається в D1 (`migrations/0001_init.sql`):

| Таблиця | Що в ній |
| --- | --- |
| `target_state` | останній стан кожної цілі |
| `target_hours`, `target_days` | лічильники перевірок, повільних, падінь, сума часу відповіді й серверного часу API |
| `target_events` | зміни стану |
| `incidents` | оголошення |
| `instances`, `instance_days` | телеметрія: останній пінг інстансу й рядок на день |
| `meta` | найновіший реліз і денний лічильник нових інстансів |

Перевірки пишуться не окремими рядками, а як лічильники години й дня, приблизно 3 записи на перевірку. Причина в ліміті безкоштовного D1: 100 тис. записаних рядків на добу на весь акаунт, і цей ліміт спільний із каталогом.

Прибирання щодня о 03:00 UTC видаляє:

- погодинні лічильники, старші за 2 доби;
- денні лічильники, старші за 400 днів;
- події, старші за 90 днів.

Найновіший реліз береться з GitHub (`RELEASES_REPO`) щогодини.

## Телеметрія

Пінг важить до 2 КБ і містить лише числа й коди:

```json
{
  "instanceId": "3f2a9c1e-5b7d-4e8a-9c21-7d4e5f6a8b90",
  "version": "v1.2.0",
  "kind": "selfhost",
  "krais": ["cz"],
  "kurins": 2, "members": 130,
  "activeUsers7d": 12, "activeUsers30d": 25,
  "requests24h": 4200, "errors24h": 3,
  "uptimeHours": 71
}
```

IP не зберігається, лише країна, яку визначає Cloudflare. Нових інстансів за добу приймається не більше 200.

## API

| Метод | Шлях | Що робить |
| --- | --- | --- |
| GET | `/v1/status` | стан для сторінки, кеш на краю 60 с |
| POST | `/v1/ping` | пінг інстансу, відповідає `{ ok, latest }` |
| GET | `/v1/admin/telemetry` | підсумки для адмінки |
| GET, POST, PATCH, DELETE | `/v1/admin/incidents` | оголошення: `incident`, `maintenance`, `notice` |
| DELETE | `/v1/admin/instances/:id` | прибрати сміттєвий інстанс |
| POST | `/v1/admin/check` | перевірити цілі зараз |

Шляхи `/v1/admin/*` пускають лише з токеном Cloudflare Access для пошти з `OWNER_EMAILS`.

## Код

| Файл | Що в ньому |
| --- | --- |
| `src/index.ts` | маршрути (Hono) і вхід крону |
| `src/checks.ts` | проба цілі, повтор, запис лічильників, тексти сповіщень |
| `src/prober.ts` | Durable Object, з якого йдуть проби, і запасний шлях без нього |
| `src/status.ts` | збирання `/v1/status`: смужки, погодинні середні, загальний стан |
| `src/cron.ts` | перевірки на кожному тіку, щоденне прибирання, найновіший реліз |
| `src/telemetry.ts` | прийом і перевірка пінгів, підсумки, сповіщення про замовклі інстанси |
| `src/auth.ts` | перевірка токена Cloudflare Access |
| `public/` | статична сторінка статусу й адмінка |
| `wrangler.jsonc` | цілі (`TARGETS`), крон, D1, домен |

## Розробка

```sh
npm test            # vitest на workerd з локальною D1

```

Пуш у `main` деплоїть воркер через Workers Builds. Нові міграції D1 накочуються окремо: `npm run db:migrate:remote`.
